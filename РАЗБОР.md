## 2. Схема — schema.sql

Вместо хранения только в списках Python подготовлены три связанные SQL-таблицы. Сам API пока использует прежние списки: подключение БД не входит в Lab 6.

- courses.id: text PRIMARY KEY — сохраняет slug из URL; title и description обязательны.
- credits: NOT NULL и CHECK > 0 — нельзя записать NULL, ноль или отрицательное число.
- is_elective: NOT NULL DEFAULT false — если значение не указано, курс обязательный.
- likes: NOT NULL DEFAULT 0 и CHECK >= 0 — начальное значение 0, отрицательные запрещены.
- students.id: bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY — номер выдаёт БД.
- students.name: NOT NULL, char_length >= 2; email: NOT NULL UNIQUE — совпадающие email запрещены.
- enrollments.id: такой же identity; course_id и student_id обязательны и защищены внешними ключами.
- ON DELETE RESTRICT запрещает удаление курса с записями; ON DELETE CASCADE удаляет записи удаляемого студента.
- enrolled_at: timestamptz NOT NULL DEFAULT now() — момент записи формируется автоматически.
- UNIQUE(course_id, student_id) запрещает повторную запись того же студента на тот же курс.

DROP TABLE в начале позволяет повторить учебную работу с чистого листа. Это удаляет данные, поэтому для реального приложения нужны миграции.

## 3. Начальные данные — seed.sql

Перенесены шесть курсов с точными значениями из data.py. Добавлены Aigerim, Daniyar и Asel, а затем шесть записей на курсы. Порядок нужен из-за FK: родительские строки должны существовать раньше дочерних. Всё обёрнуто в одну транзакцию: загрузка не должна остаться наполовину выполненной. Контроль — 6 курсов, 3 студента, 6 записей; элективных курсов 2.

## 4. Запросы — queries.sql

1. WHERE is_elective=false фильтрует обязательные курсы; ORDER BY likes DESC, id задаёт устойчивый порядок; LIMIT 3 OFFSET 0 возвращает первую страницу (24, 21, 19 лайков).
2. Вариант 1b с OFFSET 3 возвращает вторую страницу — databases-postgresql с 15 лайками. Формула смещения: (page−1)×page_size.
3. Запрос 2 получает api-design, вариант 2b возвращает 0 строк для неизвестного slug. Будущий API должен преобразовать это в 404.
4. Запросы 3/3b делают атомарный UPDATE likes=likes+1 RETURNING: для существующего курса 12, для неизвестного UPDATE 0. ROLLBACK возвращает лайки к 11.
5. Запрос 4 записывает Asel на web-security и возвращает созданную запись. ROLLBACK оставляет прежние шесть записей; номер identity при этом может быть потрачен.
6. Запрос 5 использует два JOIN, чтобы вместо технических id показать имена студентов и названия курсов.
7. Запрос 6 использует LEFT JOIN и count(e.id): показывает 3, 2, 1, 0, 0, 0 записей по курсам. count(*) ошибочно дал бы 1 для курса без записей.
8. Бонусные 7 и 8 находят курсы без студентов и студентов с несколькими курсами. HAVING фильтрует группы после подсчёта.

## 5. Ограничения — experiments/constraints.sql

Подготовлены все десять намеренных нарушений, каскадное удаление с откатом и дополнительная проверка ручного identity. В README каждому сопоставлены SQLSTATE, имя ограничения и будущий HTTP-ответ. 23514 означает CHECK, 23505 — уникальность, 23503 — FK, 23502 — NOT NULL; RESTRICT зависит от версии сервера. Отрицательные likes дают 500, потому что это ошибка внутреннего кода, а не пользовательского ввода. Ошибки в этом эксперименте ожидаемы; обычные файлы запускаются с остановкой на первой ошибке.

## 6. Индекс — experiments/idx_data.sql и index.sql

Подготовлено 500 курсов, 20000 студентов, 50000 записей, затем ANALYZE. Сценарий сравнивает запрос student_id=777 до/после индекса, делает по три EXPLAIN ANALYZE и выводит размер таблицы/индекса. В итоговую схему добавлен enrollments_student_id_idx. FK сам индекс не создаёт, а индекс UNIQUE(course_id,student_id) ориентирован прежде всего на поиск по course_id. Новый индекс полезен для записей одного студента и каскадного удаления. Фактические планы/время зависят от сервера; статус выполнения и журнал приведены в README.

## 7. Транзакции — experiments/transaction.sql

Два INSERT объединены BEGIN/ROLLBACK. Второй нарушает FK: транзакция становится аварийной, дальнейший SELECT получает 25P02. После ROLLBACK исчезает и студент из первого INSERT. Для успешного случая в README есть команды двух окон: второй клиент видит 0 до COMMIT и 1 после; это демонстрирует атомарность и read committed.

## Что реально проверено

Выполнено на PostgreSQL 18.6 от catalog_app. Все SQL-запросы совпали с примерами задания, ошибки ограничений подтверждены реальными сообщениями. План изменился с Seq Scan (cost 1042) на Bitmap Heap/Index Scan (cost 15.59); минимальное время из трёх запусков — 1.376 → 0.008 мс. Размер таблицы 3336 kB, индекса 896 kB. Два независимых соединения подтвердили 0 до COMMIT и 1 после. После опытов восстановлены 6 курсов, 3 студента, 6 записей и 11 лайков api-design. Все журналы находятся в experiments/*.log.

Обязательная часть реализована и проверена, бонус №4 выполнен. Для окончательной сдачи остаётся опубликовать репозиторий на GitHub и передать ссылку преподавателю. Сервер для демонстрации оставлен запущенным в lab6-postgres на localhost:55436; команды подключения есть в README.
