## Бонус 1. CHECK, который autogenerate не замечает, и op.f()

**Что сделал.** Во временную модель Course добавил CHECK:

```python
CheckConstraint("level IN ('beginner', 'intermediate', 'advanced')", name="level")
```

`alembic check` сообщил `No new upgrade operations detected`, а автоматически
созданная миграция содержала `pass`. В используемой версии Alembic сравнение
произвольных CHECK не выявляет такую разницу. Чистый check поэтому не доказывает
полного совпадения CHECK-ограничений: их изменение надо описать вручную.

Написал `0003` с `op.create_check_constraint(op.f("courses_level_check"), ...)`,
применил её и попробовал записать `level='expert'`. PostgreSQL отказал:
`CheckViolation`, SQLSTATE `23514`, ограничение `courses_level_check`.

В downgrade сначала передал обычную строку `"courses_level_check"`.
Откат завершился `UndefinedObject`: Alembic искал
`courses_courses_level_check_check`. Версия базы осталась `0003`.
Шаблон CHECK в naming_convention имеет вид
`%(table_name)s_%(constraint_name)s_check`: без op.f имя было обработано повторно.

**Исправление.** `op.drop_constraint(op.f("courses_level_check"), "courses", type_="check")`.
`op.f()` помечает имя как окончательное, и naming_convention больше его не расширяет.
После исправления откат до `0002` прошёл; экспериментальные CHECK и файл `0003` удалены.

Сохранены отдельные примеры:
[пустой autogenerate](experiments/bonus_artifacts/01_check_autogenerated.py.txt),
[ошибочный downgrade](experiments/bonus_artifacts/01_check_broken_downgrade.py.txt),
[исправленная миграция](experiments/bonus_artifacts/01_check_fixed.py.txt).
Это текстовые артефакты, которые Alembic не применяет.

**На защите:** «CHECK добавил вручную, потому что autogenerate его не обнаружил.
В upgrade и downgrade обернул готовое имя в op.f, чтобы шаблон не применился дважды».

## Бонус 2. Переименование колонки без потери данных

**Что сделал.** Сохранил исходные описания всех шести курсов, во временной модели
заменил `description` на `summary` и запустил autogenerate. Он предложил
`add_column(summary, nullable=False)` и `drop_column(description)`.
Alembic видит исчезнувшее и появившееся имя, но не может достоверно угадать,
что это именно переименование. Такой черновик на заполненной таблице сначала
столкнулся бы с NOT NULL, а удаление старого столбца уничтожило бы описания.
Опасный черновик не применял.

**Исправление.** Заменил операции на:

```python
def upgrade():
    op.alter_column("courses", "description", new_column_name="summary")

def downgrade():
    op.alter_column("courses", "summary", new_column_name="description")
```

После upgrade `alembic check` чистый. Сравнил пары `(id, summary)` с исходными
`(id, description)` — совпали все шесть, включая полные тексты. Проверил обратное
переименование через downgrade: тексты опять совпали. Восстановил модель и удалил `0003`.

Артефакты: [черновик add/drop](experiments/bonus_artifacts/02_rename_autogenerated.py.txt),
[безопасная миграция](experiments/bonus_artifacts/02_rename_fixed.py.txt).

**На защите:** «alter_column с new_column_name меняет имя существующей колонки
и сохраняет её значения; add/drop создаёт другой столбец и удаляет прежний с данными».

## Бонус 3. Проблема N+1

Скрипт: [try_n_plus_1.py](try_n_plus_1.py).

**Что сделал.** После прогрева подключения подписался на `before_cursor_execute`
и посчитал запросы при обходе курсов и их записей. Для каждого варианта открывал
новую сессию, чтобы загруженные объекты не повлияли на результат.

| Загрузка | Записей на курсы | SQL-запросов |
|---|---:|---:|
| Обычная lazy | 6 | 7 |
| selectinload | 6 | 2 |

Lazy сначала получает шесть курсов одним SELECT, затем обращение к
`course.enrollments` вызывает ещё SELECT для каждого курса: 1 + 6.
`selectinload(Course.enrollments)` загружает курсы первым запросом,
а записи для всех этих курсов — вторым, с `WHERE course_id IN (...)`.

**Как заметить.** Включить `SQL_ECHO=true` и найти серию одинаковых по структуре
SELECT, отличающихся только course_id, либо посчитать запросы событием SQLAlchemy.

**Отличие joinedload.** Он загружает связанные строки JOIN в одном запросе,
но повторяет данные курса для каждой записи. При загрузке коллекции через
joinedload в SQLAlchemy 2.x результат надо дедуплицировать с `unique()`.
selectinload делает дополнительный SELECT и избегает такого размножения строк
основного результата; для очень больших наборов возможны несколько пакетов IN.
В этом опыте сравнены требуемые lazy и selectinload.

**На защите:** «Количество результатов одинаковое, но lazy сделал 7 запросов,
а selectinload — 2. Это устраняет запрос на каждый отдельный курс».

## Бонус 4. Потерянное обновление лайков

Скрипт: [try_lost_update.py](try_lost_update.py).

**Что сделал.** Две независимые сессии Alice и Bob прочитали 11 лайков.
В первом варианте каждая увеличивала число в Python и сохраняла результат.
Во втором варианте присваивал SQL-выражение `Course.likes + 1`.
Перед каждым вариантом восстанавливал seed.

| Вариант | Прочитали Alice / Bob | Итог |
|---|---|---:|
| `a.likes = a.likes + 1` | 11 / 11 | 12 |
| `a.likes = Course.likes + 1` | 11 / 11 | 13 |

В первом варианте оба вычислили 12 и отправили `SET likes=12`.
Даже после первого commit у Bob осталось ранее прочитанное значение 11.
Поэтому второй commit затёр результат первым же числом: один лайк потерялся.

Во втором варианте БД выполняет `SET likes=likes+1` и вычисляет новое значение
по текущей строке. UPDATE получает блокировку строки; конкурирующий UPDATE ждёт
завершения первой транзакции, затем увеличивает актуальное значение при обычном
READ COMMITTED. Это связь с блокировками Lab 6. Блокировки сами по себе
не исправляют `SET likes=12`: необходимо атомарное выражение или другой
согласованный протокол чтения/блокировки. В этом воспроизводимом опыте commit
выполняются последовательно после двух чтений, чтобы гарантированно показать ошибку.

После обоих вариантов seed восстановлен; рабочий маршрут лайка уже использует
атомарный `UPDATE ... RETURNING`.

**На защите:** «Два чтения 11 и две записи 12 дают потерянное обновление.
В SQL-выражении БД дважды увеличивает текущее число и получает 13».

## Бонус 5. passive_deletes и каскад PostgreSQL

Скрипт: [try_delete.py](try_delete.py).

**Что сделал.** Во временной модели убрал passive_deletes=True только у
Student.enrollments. Попытка удалить студента 3 закончилась NotNullViolation:
ORM загрузил его записи и попытался выполнить UPDATE с `student_id=NULL`.
Внешний ключ обязательный, поэтому база отказала; после ошибки осталось
3 студента и 6 записей.

Вернул passive_deletes=True и повторил удаление в новой сессии, где коллекция
записей не была загружена. ORM удалил студента, а PostgreSQL выполнил
ON DELETE CASCADE: осталось **2 студента и 5 записей**. Курсы не изменились.

passive_deletes сообщает ORM, что незагруженные дочерние строки обрабатывает БД;
само каскадное правило задаёт `ForeignKey(..., ondelete="CASCADE")`.
Для уже загруженных коллекций поведение также зависит от настройки ORM cascade;
этот опыт, как и задание, использует свежую сессию и незагруженную коллекцию.
В конце seed восстановлен до **6 курсов / 3 студентов / 6 записей**.

**На защите:** «Без passive_deletes ORM пытается обнулить обязательный FK.
С ним удаление незагруженных дочерних записей выполняет PostgreSQL по CASCADE».

## Повторить все бонусы

Из каталога API, с работающим lab7-postgres. Один раз создать отдельную базу
от суперпользователя PostgreSQL:

```sql
CREATE DATABASE lab7_bonus_20261112 OWNER catalog_app;
```

```bash
source .venv/bin/activate
DATABASE_URL=postgresql+psycopg://catalog_app:change-me@localhost:5437/lab7_bonus_20261112 \
  python experiments/run_bonus.py
```

Адрес задаётся только на время команды, рабочий `.env` не меняется.
Runner сбрасывает public schema исключительно базы с этим точным именем,
применяет миграции, восстанавливает seed между опытами, проверяет результаты
и удаляет временную копию исходников при завершении. При успешном запуске:

```text
ALL FIVE BONUSES PASSED; models, migrations and seed restored
```

После запуска из PostgreSQL-базы `postgres` удалить экспериментальную базу:

```sql
DROP DATABASE lab7_bonus_20261112;
```

В итоговом `alembic/versions` остаются только 0001 и 0002. Контроль после бонусов:
одна head 0002, alembic check без различий, check_models без расхождений,
пять интеграционных тестов прошли. README содержит отдельный краткий раздел Bonus.
